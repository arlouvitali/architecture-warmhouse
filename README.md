# Project_template

# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.

**Мониторинг температуры:**

- Система получает данные о температуре с датчиков, установленных в домах.
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.

### 2. Анализ архитектуры монолитного приложения

Язык программирования: Go
База данных: PostgreSQL
Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
Взаимодействие: Синхронное, запросы обрабатываются последовательно.
Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

На основе анализа приложения выделены следующие домены:

- **Device Management (Управление устройствами):** Включает CRUD-операции для сенсоров (датчиков), управление их состоянием (включено/выключено), хранение метаданных о сенсорах.
- **Monitoring (Мониторинг):** Получение и отображение данных о температуре из внешнего API, обновление значений сенсоров в реальном времени.

Границы контекстов: Device Management отвечает за хранение и управление сенсорами в БД, Monitoring - за интеграцию с внешним temperature-api для получения актуальных данных.

### **4. Проблемы монолитного решения**

- **Низкая масштабируемость:** Монолит сложно масштабировать по частям; при росте нагрузки приходится масштабировать всё приложение целиком.
- **Сложность развертывания:** Изменения требуют перезапуска всего приложения, что увеличивает время простоя.
- **Зависимость от внешних сервисов:** Синхронное взаимодействие с temperature-api может привести к блокировке всего приложения при сбоях внешнего сервиса.
- **Трудности в разработке:** Все компоненты в одном коде, что усложняет параллельную разработку и тестирование отдельных частей.

# Задание 2. Проектирование микросервисной архитектуры

**Диаграмма контейнеров (Containers)**

Диаграмма контейнеров представлена в файле [diagrams/containers_diagram.puml](diagrams/containers_diagram.puml).

Она показывает основные контейнеры: Mobile App (внешний), API Gateway, Identity Provider Service, Device Management Service, Monitoring Service, Scenario Service, базы данных (PostgreSQL для каждого сервиса), Message Broker (RabbitMQ для асинхронного взаимодействия), WiFi Router (для взаимодействия с Device Modules). Взаимодействие с внешними Device Modules происходит синхронно через HTTPS для получения телеметрии и отправки команд. Mobile App взаимодействует с Device Modules напрямую через локальную сеть для регистрации и управления.

**Диаграмма компонентов (Components)**

Она детализирует компоненты внутри сервиса: API Handler, Device Service (бизнес-логика), Device Repository, Command Sender (отправка команд устройствам через HTTPS).

**Диаграмма кода (Code)**

Диаграмма последовательности для получения температуры представлена в файле [diagrams/code_diagram.puml](diagrams/code_diagram.puml).

# Задание 3. Разработка ER-диаграммы

ER-диаграмма представлена в файле [diagrams/er_diagram.puml](diagrams/er_diagram.puml).

Ключевые сущности:
- User: id (PK), name, email, password_hash
- House: id (PK), user_id (FK), name, address
- Room: id (PK), house_id (FK), name
- DeviceType: id (PK), name
- Device: id (PK), room_id (FK), type_id (FK), name, router_ip, mac_address, status
- TelemetryRecord: id (PK), device_id (FK), value, unit, timestamp
- Scenario: id (PK), house_id (FK), name, description, schedule, conditions (JSONB), actions (JSONB), status

Связи:
- User 1-* House
- House 1-* Room
- Room 1-* Device
- House 1-* Scenario
- Device *-1 DeviceType
- Device 1-* TelemetryRecord

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия микросервисов выбран REST API, так как он подходит для синхронного взаимодействия, когда нужен немедленный ответ. Для асинхронных сценариев (например, отправка команд устройствам) можно использовать AsyncAPI с очередями сообщений.

### 2. Документация API

Документация API представлена в файлах:
- Device Management API: [api/device_api.yaml](api/device_api.yaml) (эндпоинты для CRUD домов, комнат, типов устройств, устройств)
- Monitoring API: [api/monitoring_api.yaml](api/monitoring_api.yaml) (эндпоинты для получения и создания телеметрии)
- Scenario API: [api/scenario_api.yaml](api/scenario_api.yaml) (эндпоинты для CRUD сценариев с полем status для активации/деактивации)
